# 0035 — Schema migrations: Alembic from the models, owner and runtime roles, a migrate job

- Status: Proposed
- Date: 2026-11-08
- Deciders: project owner
- Brief reference: §1 Database, §3.6, §3.8

## Context and problem statement

The brief requires SQLAlchemy 2 and Alembic for every schema change. The backend runs as several stateless replicas and handles decrypted code in memory, so the role it connects with should not be able to change the schema.

## Decision drivers

- One source of the schema, checked against the migrations.
- Least privilege for the process that serves requests.
- Migrations applied exactly once per deploy, before new replicas serve.

## Considered options

1. **Models as the source; autogenerated, hand-reviewed Alembic revisions; an owner role for migrations and a DML-only runtime role; a one-shot `migrate` service.**
2. The backend applies migrations at startup under an advisory lock (template_core D-004), with one role.

## Decision outcome

Chosen option: **1**.

- `common_lib.models` holds the SQLAlchemy 2 models (18 tables, `vector(1024)` with an HNSW cosine index, TIMESTAMPTZ everywhere, deterministic constraint names). Only the backend and the migrations import it (import-linter).
- `server/migrations`: revisions are generated with `alembic revision --autogenerate` against an empty database, then reviewed and edited by hand. Revision `0001` is the Phase 0 schema.
- Roles (`deploy/docker/postgres/initdb/`): the **owner** owns the database and the `public` schema and is used only by the migrate job; the **app** role (the backend) gets `SELECT, INSERT, UPDATE, DELETE` on tables and sequence usage through default privileges, and no `CREATE`. pgvector is created by the superuser at init; the migration's `CREATE EXTENSION IF NOT EXISTS` is a no-op that fails clearly when it is missing.
- Alembic's version table lives in a `migrations` schema owned by the owner, with no access for the app role, so the runtime role cannot rewrite migration state. Database provisioning creates that schema (initdb locally); Alembic does not.
- Privacy in the schema: code-derived ids are `CHAR(64)` with a `CHECK` for lowercase HMAC hex; `repositories.remote_url` has a `CHECK` against any userinfo (`ssh://git@host/...` is rejected too; the registration API stores the https form); repository and project names and remote URLs are metadata allowed in clear. `*_enc` columns hold a versioned envelope `version (1 byte) || key_id || nonce (12) || ciphertext || tag (16)`, written and read with the crypto of ADR-0015 (Phase 2). A unit test keeps a reviewed allow-list of every text and JSON column.
- Compose runs `migrate` (`alembic upgrade head` with the owner role, from the backend image) before the backend starts.
- The backend has a write engine and a read engine (`DB_READ_HOST`, the primary when unset) with their session factories (brief §3.8).
- Revision `0003` renames `projects.company_os_ref` to `projects.external_ref` (values kept): the project's id in the project-context system, read by the project-context connector.
- Revision `0004` adds `repository_keys`, each repository's HMAC key wrapped under the KEK, and replaces the `remote_url` CHECK with one that allows only the forms registration stores (ADR-0016).
- Revision `0005` adds `code_chunks.leaf_node_id` and keys chunks by `(repository_id, leaf_node_id)` (ADR-0020).

### Consequences

- Good: a compromised backend cannot alter or drop tables; the schema is the same in tests and compose.
- Good: `tests/integration/test_migrations.py` proves the migrations build exactly the models' schema and that downgrade works.
- Bad: an existing local volume must be recreated to get the new roles (initdb runs once).
- Bad: one more one-shot service in the start order.
- Note: `REVOKE ALL ON DATABASE ... FROM PUBLIC` also removes `TEMP`; the app role cannot create temporary tables. A bulk-load path that needs them grants `TEMP` explicitly.

### Confirmation

`tests/integration/test_migrations.py`: upgrade on the real init script and image, `compare_metadata` is empty, the app role can write rows but `CREATE`, `DROP` and `TRUNCATE` fail, downgrade and upgrade again.
